# Атоми — обращения и Telegram

Личный тестовый проект владельца `elizavetavozba-debug`. Форма на обычных HTML/CSS/JavaScript; данные и транзакции в Supabase PostgreSQL; события Telegram обрабатывают Edge Functions. Компьютер владельца для работы не нужен. Платные API и ИИ в обработке обращений не используются.

## Фактическое подключение

Репозиторий: https://github.com/elizavetavozba-debug/atomi-requests

Предусмотренный адрес GitHub Pages: https://elizavetavozba-debug.github.io/atomi-requests/

На момент подготовки исходников Supabase и Telegram **ещё не подключены**. `public/config.js` оставлен пустым, форма отключена. Это не подтверждение работающего запуска. Точные адреса функций, имя бота и результаты живой приёмки добавляются после подключения аккаунтов. В production нет фиктивных обращений: автотесты работают исключительно в отдельной локальной PGlite.

GitHub Pages выбран владельцем для личного теста. [Правила Pages](https://docs.github.com/en/site-policy/github-terms/github-terms-for-additional-products-and-features) запрещают использование как бесплатного хостинга для ведения онлайн-бизнеса и сайтов, преимущественно содействующих коммерческим сделкам. Перед переходом к продажам косметики нужно согласовать другое допустимое размещение.

## Обращение

1. Форма отправляет имя (1–80), тему (1–120), описание (5–2000) в `create-application`. HTTPS, точный CORS origin, ловушка, ограничения тела и частоты. Браузер сохраняет введённый текст при сетевой ошибке, UUID остаётся тем же для повтора одинаковых данных.
2. Транзакция создаёт только `draft`. Код ссылки — HMAC-SHA256 от UUID с `FORM_SECRET`, 43 URL-safe символа. В БД хранится SHA-256 кода, срок 30 минут. Ссылку нельзя пересылать.
3. Только личный Start в боте атомарно привязывает обращение к Telegram ID и переводит его в `new`. Повтор не создаёт новое обращение; другой аккаунт не может перепривязать заявку.
4. Бот выдаёт клиенту номер, владельцу — карточку. Ответы принимаются только через ForceReply с постоянной привязкой `(chat_id, message_id)` к обращению. Свободный текст предлагает выбрать карточку.
5. Сообщение сначала сохраняется в PostgreSQL, затем ставится в outbox. Отправитель сначала получает «сохранено», затем отдельное подтверждение фактической доставки или сообщение об ошибке. Подтверждённые обращения и переписка автоматически не удаляются.

## Команды бота

- `/requests` — владелец: новые, в работе, все; по 8 на страницу.
- `/my` — только свои обращения, статус, история и уточнения.
- `/id` — только собственный Telegram ID. Эта команда не назначает владельца.
- `/retry` — только владелец: ошибки доставки и безопасный повтор.

Статусы: `draft`, `new`, `in_progress`, `done`. Закрытие сохраняет переписку. Карточка владельца: «Ответить», «История», «В работу», «Завершить». Вложения, платежи, голосовые сообщения и ИИ-ответы не поддерживаются. Переписка — текст до 2000 символов.

## Локальные команды

Требуется Node.js 22+ и npm. Зависимость PGlite нужна только для тестов; сайт не требует сборки.

```sh
npm ci
npm test
npm run check
npm run bundle
npm run preview
```

Предпросмотр: `http://127.0.0.1:4173/atomi-requests/`. Веб-сервер отдаёт исключительно `public/`; секреты недоступны. `npm run bundle` создаёт `.local/dashboard/create-application.ts`, `telegram-hook.ts`, `setup-telegram.ts`: каждый файл самостоятельный, без импортов соседних файлов, пригоден для Supabase Dashboard Editor.

## Секреты

Файл `.local/secrets.env` имеет права 600, папка — 700. `.local/`, `.env*`, `supabase/.temp/`, `supabase/.branches/` исключены из Git. Токены и ключи запрещено вставлять в чат, Git, README, скриншоты или браузерный config.

В Edge Functions Secrets хранятся `BOT_TOKEN`, `BOT_USERNAME` (без @), `ADMIN_CHAT_ID`, `SITE_URL` (полный адрес с `/atomi-requests/`), `TG_WEBHOOK_SECRET`, `SETUP_SECRET`, `FORM_SECRET`. Три независимых криптографических секрета генерируются локально; каждый 43 URL-safe символа. В webhook-секрете только допустимые Telegram символы.

Поддерживаются встроенные `SUPABASE_URL`, `SUPABASE_SECRET_KEYS` (строка либо JSON-словарь: default или первое строковое значение), `SUPABASE_SERVICE_ROLE_KEY` и явный `SERVER_DB_KEY`. Для новых ключей `sb_secret_` REST RPC использует `apikey`, без ошибочного Bearer с непрозрачным ключом; для старого JWT также `Authorization: Bearer`. Серверный ключ никогда не передаётся браузеру.

До проверки `ADMIN_CHAT_ID` создание форм отключено. Владелец определяется только по этому ID и `from.id`, а не username, полю формы или первому посетителю.

## Подключение и обновление Supabase

Используется только согласованный отдельный проект организации на Free. Новый пароль базы задаёт сам владелец. Чужие проекты и существующие таблицы не изменяются.

Миграции применяются один раз строго по порядку:

1. `supabase/migrations/202611070001_schema.sql`
2. `supabase/migrations/202611070002_rpc.sql`

Все пять таблиц находятся в `requests_app`: `tickets`, `messages`, `updates`, `outbox`, `prompts`. Везде включён RLS без клиентских политик, доступ `anon`/`authenticated` к схеме, таблицам, последовательностям и RPC отозван. Только `service_role` может выполнять публичные `nr_create_draft`, `nr_handle_update`, `nr_claim_outbox`, `nr_delivered`, `nr_failed`, `nr_pending_count`. У функций фиксирован безопасный `search_path`. Схему `requests_app` не нужно добавлять к exposed schemas API.

Размещаются три функции из `supabase/functions/` либо самостоятельных файлов bundle. **Только** у этих трёх функций отключается стандартная проверка JWT: форма публична и имеет серверную валидацию; webhook проверяет `X-Telegram-Bot-Api-Secret-Token`; setup проверяет `X-Setup-Secret`. Нельзя отключать защиту других функций или базы. CORS не является авторизацией.

Временная `setup-telegram` принимает POST JSON с действиями:

- `register` — проверяет имя собственного бота через getMe, устанавливает HTTPS webhook с секретом, `allowed_updates: message, callback_query`, без сброса накопленных updates.
- `status` — getWebhookInfo, совпадение ожидаемого URL, pending count и последние ошибки.
- `test` — явно обозначенное служебное сообщение проверенному владельцу.

Все рабочие обращения к Telegram и установка webhook выполняются облаком Supabase. Прямое открытие `api.telegram.org` на компьютере и VPN не обязательны.

Проверка владельца без прямого доступа к Telegram API: сначала подключить webhook, оставив `ADMIN_CHAT_ID` пустым; владелец пишет `/id` собственному боту из своего личного аккаунта; сохраняется выданный ID. До этого приём отключён. `node scripts/owner.mjs` объясняет этот путь. Альтернативный `--direct-telegram` явно запускает одноразовую проверку со случайной фразой, сначала проверяет отсутствие webhook и отказывается вызывать getUpdates при работающем webhook.

После успешной проверки и живой приёмки удаляется **только развёрнутая** `setup-telegram`, исходник сохраняется. Нужно проверить её недоступность, а также работу двух оставшихся функций. Изменение GitHub **не** применяет SQL и **не** обновляет Edge Functions. Обновление серверного кода требует повторного размещения нужной функции; изменения схемы — новой миграции, без сброса базы.

## Надёжность и восстановление

Outbox хранит `pending`, `processing`, `sent`, `failed`, уникальный ключ эффекта, число попыток, код ошибки, `lease_token`, `leased_until`. Захват использует блокировки строк с `SKIP LOCKED`, аренду 60 секунд; одна запись не выдаётся параллельным обработчикам. Для одного чата сохраняется порядок сообщений. Просроченная аренда восстанавливается при следующем webhook или его повторе. Непустая pending/processing очередь возвращает повторяемую ошибку webhook; минутных таймеров нет.

Если ответ на ForceReply пришёл раньше фиксации Telegram message_id, транзакция откатывается вместе с update_id, а webhook возвращает 503, чтобы Telegram повторил событие. Повторный update_id не создаёт повторную переписку. После ошибки Telegram запись сохраняется в failed; владелец устраняет причину и запускает `/retry`. Ошибка не отмечается успехом. Если отправка в Telegram успешна, но процесс аварийно завершился до записи результата в БД, при восстановлении возможна повторная доставка: Telegram не обеспечивает абсолютное exactly-once для sendMessage.

Если бот заблокирован, нужно разблокировать и выполнить `/retry` владельцем. Если проект Supabase приостановлен, владелец восстанавливает его в Dashboard, затем проверяются webhook status, очереди и отправка. При продолжительном простое Telegram хранит необработанные updates ограниченное время, поэтому автоматическое восстановление всех пропущенных событий не гарантируется. Заявки, уже записанные в БД, остаются. Перед существенными миграциями сделайте отдельную защищённую резервную копию; Free не обещает платные средства восстановления.

Серверные лимиты: 10 новых форм с одного хешированного IP за 10 минут, 500 за сутки UTC; 30 Telegram-действий одного человека в минуту; HTTP JSON формы до 16 KiB, update до 64 KiB, setup до 1 KiB. Для IP используется forwarding-заголовок шлюза Supabase, не данные формы; при развёртывании надо проверить его наличие и корректность на реальном шлюзе. При смене прокси источник доверенного IP пересматривается. Хеш IP не хранит исходный IP, но остаётся частью технических данных.

[Supabase Free](https://supabase.com/pricing) имеет квоты, в частности 500 MB БД, 5 GB исходящего трафика и лимиты вызовов Edge Functions. Неактивный проект может быть приостановлен после недели низкой активности. Бесплатный тариф не означает неограниченную нагрузку или гарантированную доступность; доступность зависит также от провайдера и региона. Платный план, карта и автоматическое платное расширение не подключаются.

## Приёмка

Локальные тесты применяют обе реальные SQL/PLpgSQL-миграции к отдельной PGlite, используют тестовый Telegram-транспорт и проверяют обмен двух клиентов с владельцем, идемпотентность форм/Start/update, срок ссылки, обратный порядок ответов двум заявкам одного клиента, права и поддельные callback, RLS, повтор после ошибки, lease, быстрый ForceReply, заголовки секретов, CORS, размеры, частоту и современные ключи.

Живая приёмка выполняется отдельно с ведома владельца через опубликованный сайт: явно названное контрольное обращение → Start → номер и карточка → `/requests` → ForceReply-ответ → фактическое получение → история → уточнение → смена статуса → сверка PostgreSQL и outbox. Это не заменяется тестами. Проверка двух **реальных** заявителей требует двух отдельных Telegram-аккаунтов; при одном аккаунте предел проверки фиксируется честно. Дополнительно рекомендуется проверка с телефона при выключенном компьютере владельца. Реальные обращения не удаляются.
